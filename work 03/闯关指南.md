| 占空比变量 | `duty_r` / `duty_g` / `duty_b`，由主循环按时间推进 |

## 3. 第 1 关：Timer 定时闪烁基线

**目标**：搞懂 `machine.Timer` 怎么用，理解“回调函数在中断里被自动调用”，为后面在回调里数 tick 打基础。

### 3.1 三种 PWM 路线先有个印象

| 路线 | 谁在产生波形 | CPU 负担 | 主循环能否干别的 |
|---|---|---|---|
| 软件延时（work2） | 主循环里的 `for` + `sleep_us` | 几乎全占 | 不能 |
| 硬件 PWM 外设（`machine.PWM`） | PWM 外设自己 | 几乎为零 | 能 |
| **定时器中断（本周）** | 定时器回调 | 每 1ms 一点点 | **能** |

本周走第三条路：只借定时器“每 1ms 打断我一下”，比较和引脚翻转都在回调里自己做。

### 3.2 `machine.Timer` 的基本用法

```python
timer = Timer()
timer.init(period=500, mode=Timer.PERIODIC, callback=on_tick)
```

- `period`：周期，单位**毫秒**，整数；
- `mode=Timer.PERIODIC`：周期模式，每隔 `period` 调一次回调；
- `mode=Timer.ONE_SHOT`：只触发一次（第 8 关选做会用到）；
- `callback`：到点后自动调用的函数，**必须带一个参数**（定时器对象本身），例如 `def on_tick(timer):`。

回调不是普通函数调用，它会在你主循环执行到一半时“插队”执行，这叫**中断**。所以回调必须短。

### 3.3 填空骨架

把 `main.py` 改成下面内容，自己补 `____`：

```python
from machine import Pin, Timer

BLINK_MS = ____              # 500

led = Pin(____, Pin.OUT)     # 红灯 GP10
state = 0


def toggle(timer):
    global ____
    state = ____ - state     # 0 → 1 → 0 → 1
    led.value(____)


timer = Timer()
timer.init(period=____, mode=Timer.PERIODIC, callback=____)

while True:
    pass
```

参考现象：红灯亮 0.5 秒、灭 0.5 秒，循环。主循环里只有 `pass`，灯仍然闪——因为闪灭是定时器干的，不是主循环干的。

### 3.4 两个必须理解的细节

1. **回调参数不能省**：`def toggle(timer):` 里的 `timer` 是定时器传进来的，去掉会报 `TypeError`。
2. **改全局变量要 `global`**：`state = 1 - state` 是在回调里重新绑定全局名 `state`，所以必须写 `global state`；只读取 `led` 则不用。

- [ ] 能说出 `period` 的单位是毫秒、`Timer.PERIODIC` 的含义；
- [ ] 能解释回调为什么会“插队”执行；

## 4. 第 2 关：理解“定时器数出来的 PWM”

**目标**：在写代码前，能用 tick、计数器、比较、清零四个词说清定时器 PWM 的原理，并会算 PWM 频率。

### 4.1 一个 PWM 周期是怎么“数”出来的

定时器每 `TICK_MS` 毫秒打断一次，我们在回调里维护一个计数器：

```text
每来一个 tick：
    计数器 + 1
    如果计数器 >= TICKS：计数器清零
    如果计数器 < 应该亮的 tick 数：输出高
    否则：输出低
```

一个 PWM 周期 = `TICKS` 个 tick。占空比 = 高电平 tick 数 / `TICKS`。

### 4.2 频率怎么算

```text
PWM 周期 = TICK_MS × TICKS（毫秒）
PWM 频率 = 1000 / (TICK_MS × TICKS)（Hz）
```

默认值：`TICK_MS = 1`、`TICKS = 100`：

- 周期 = 1ms × 100 = 100ms；
- 频率 = 1000 / 100 = **10Hz**。

占空比换算成“亮的 tick 数”：

```python
on = duty * TICKS // 100
```

- `duty` 是 0–100 的百分比，`on` 是 0–`TICKS` 的整数；
- `//` 是整数除法，保证 `on` 是整数；
- `TICKS = 100` 时 `on` 正好等于 `duty`。

### 4.3 10Hz 的问题：为什么任务书说“无闪烁”却给了 10Hz

10Hz 意味着每 100ms 一个周期。duty = 50% 时，灯亮 50ms、灭 50ms——人眼会清楚地看到**闪烁**，而不是稳定的半亮。人眼的“视觉暂留”大约在 50–60Hz 以上才把快速亮灭看成平均亮度。

任务书里 `TICK_MS = 1` 且切成 100 份，只能得到 10Hz；但括号里写了“**完成后可自行调整**”。这就是留给你调的地方。

在 `TICK_MS` 固定为 1ms（这台板子上 `period` 是整数毫秒，1ms 已是实用下限）时：

| TICKS | PWM 周期 | PWM 频率 | 亮度档位 | 现象 |
|---|---|---|---|---|
| 100 | 100ms | 10Hz | 101 档（1% 一档） | 明显闪烁 |
| 50 | 50ms | 20Hz | 51 档（2% 一档） | 闪烁减轻，仍能看出 |
| **20** | **20ms** | **50Hz** | **21 档（5% 一档）** | **基本平滑，推荐** |
| 10 | 10ms | 100Hz | 11 档（10% 一档） | 很稳，但亮度台阶粗 |

**取舍**：tick 数越多，亮度越细腻，但频率越低、越容易闪；tick 数越少，频率越高，但亮度台阶越粗。第 4 关会让你亲手对比。

> 如果一定要“100 档 + 高频率”，得让 tick 小于 1ms（查 `Timer` 的 `freq` 参数），这超出本周任务书要求，第 8 关作为选做提一句。

### 4.4 为什么定时器 PWM 能解放 CPU

软件延时方案里，CPU 必须一直在循环里“亮—等待—灭—等待”；定时器方案里，CPU 平时跑主循环，只有每 1ms 被中断“借走”几微秒去更新一次引脚。所以主循环可以同时改占空比、打印串口、处理按键。

代价是：回调必须短。回调一旦卡住，主循环和下一次中断都会被拖慢。

## 5. 第 3 关：单路定时器 PWM

**目标**：把第 1 关的“翻转引脚”换成“按计数器与占空比比较”，在主循环里扫描 duty，让红灯呼吸。

### 5.1 常量先行

文件开头把参数写成命名常量，后面调参只改这里：

```python
TICK_MS = ____       # 定时器中断周期，毫秒
TICKS = ____         # 一个 PWM 周期的 tick 数
DUTY_STEP = ____     # duty 每次变化几个百分点
BREATH_MS = ____     # 主循环每一拍停多久，毫秒
```

建议初值：`TICK_MS = 1`、`TICKS = 100`、`DUTY_STEP = 1`、`BREATH_MS = 20`。

### 5.2 回调只做三件事

```python
count = 0


def on_tick(timer):
    global count
    count = (____ + 1) % TICKS
    led.value(____ if count < duty * TICKS // 100 else ____)
```

逐行解释：

- `count = (count + 1) % TICKS`：计数 0,1,…,`TICKS-1`，到 `TICKS` 自动回 0，这就是“计满清零”；
- `duty * TICKS // 100`：把 0–100 的百分比折算成 0–`TICKS` 的 tick 数；
- `1 if count < on else 0`：条件表达式，条件成立取 1（点亮），否则取 0（熄灭）；
- `on = duty * TICKS // 100` 可以直接写进条件里，也可以先算出来再比较，两种都可以；注意回调里不要做多余计算。

`count` 是全局变量又在回调里重新赋值，所以**必须**写 `global count`；`duty` 只读，不用 `global`。

### 5.3 主循环只负责“改 duty”

```python
duty = 0

while True:
    for duty in range(0, 101, DUTY_STEP):
        time.sleep_ms(BREATH_MS)
    for duty in range(100, -1, -DUTY_STEP):
        time.sleep_ms(BREATH_MS)
```

要点：

- 主循环里的 `for duty in ...` 在模块层，`duty` 就是全局变量，回调每 1ms 读到的就是它；
- 这里**不需要**在循环里调用任何生成波形的函数——波形由定时器持续产生；
- `range(0, 101, 1)` 产生 0…100；反向 `range(100, -1, -1)` 终点写 **-1** 才能取到 0；
- 呼吸一次约 `2 × 101 × BREATH_MS`，`BREATH_MS = 20` 时约 4 秒（实际略长，中断和 Python 开销会占一点）。

### 5.4 先别呼吸：固定 duty 测试

把主循环临时改成：

```python
duty = 50
while True:
    pass
```

现象（`TICKS = 100`，10Hz）：灯能看到明显的亮灭闪烁，但平均亮度约为一半。这说明波形已经在定时器里跑起来了。再试 `duty = 0`（全灭）、`duty = 100`（最亮）、`duty = 10`（很暗）。

> 10Hz 下“半亮”看起来是“闪”，不是“稳稳的半亮”。这是正常的，第 4 关调到 50Hz 后就平滑了。先确认 duty 能控制平均亮度，再回去做呼吸。

### 5.5 验收

- [ ] `duty = 0` 全灭，`duty = 100` 最亮，`duty = 50` 平均半亮；
- [ ] 回调只有计数、比较、`value` 这几行，没有 `sleep`、没有 `print`；
- [ ] `count` 取模 `TICKS`，计满能清零；
- [ ] `TICK_MS`、`TICKS`、`DUTY_STEP`、`BREATH_MS` 是文件开头的命名常量；
- [ ] 红灯能从暗到亮再到暗循环。

### 5.6 排错顺序

**灯先能亮 → 定时器 period 是否设置 → `global count` 是否漏写 → `on` 计算 → 主循环 duty 是否真的在变 → 反向 range 端点**。

## 6. 第 4 关：回调纪律与四个验收实验

**目标**：把“波形归定时器、节奏归主循环”这件事彻底验证清楚，并把闪烁调掉。

### 6.1 实验一：固定 duty + 主循环空转

```python
duty = 50

while True:
    pass
```

- 现象：灯保持平均半亮（10Hz 时会闪，但不会灭掉或乱跳）；
- 结论：**波形的产生完全不依赖主循环**。主循环什么都不做，定时器照样每 1ms 更新引脚。

### 6.2 实验二：把呼吸用的 `sleep_ms` 改成 `pass`

按任务书验收第 2 条，把主循环改成：

```python
while True:
    for duty in range(0, 101, DUTY_STEP):
        pass
    for duty in range(100, -1, -DUTY_STEP):
        pass
```

**你要如实观察到的现象**：灯不会灭，波形也还在，但 duty 扫描快到肉眼几乎看不出呼吸，看起来接近一个固定亮度。

这条验收要拆成两句话理解：

1. **“波形不依赖主循环的延时”**——成立。证据就是实验一：固定 duty、主循环 `pass`，灯照样被定时器驱动。
2. **“灯仍然正常呼吸”**——不严格成立。呼吸的快慢本来就是主循环用 `sleep_ms` 调出来的；去掉 sleep，节奏自然失控。这不是你的 bug，而是任务书把两件事写在一句话里了。

**怎么向老师演示**：先做实验一证明波形来自定时器；再按字面把 sleep 改 `pass`，说明“呼吸节奏变快但波形没停”；最后恢复 `sleep_ms`，呼吸恢复正常。三句话就能讲清楚职责分离。

> 如果老师坚持要“改成 pass 后还按正常速度呼吸”，那只能把呼吸也搬进中断（在回调里按 tick 计数改 duty），但这会违反本周“回调不超过 10 行、不延时”的约束，不建议为了凑现象去改架构。

### 6.3 实验三：改 `TICK_MS`

把 `TICK_MS` 从 1 改成 2，其他不动：

- PWM 周期 = 2ms × 100 = 200ms；
- PWM 频率 = 1000 / 200 = **5Hz**；
- 闪烁更明显，呼吸速度基本不变（呼吸由主循环控制）；
- 结论：`TICK_MS` 改变的是**波形周期/频率**，不是呼吸速度。

改回 1，再试 `TICK_MS = 5`（2Hz），观察闪烁有多严重。

### 6.4 实验四：改 `TICKS`，调掉闪烁

把 `TICKS` 从 100 改成 **20**：

- PWM 周期 = 1ms × 20 = 20ms；
- PWM 频率 = **50Hz**；
- 灯明显平滑，肉眼基本看不到闪烁；
- 代价：亮度只有 21 档（5% 一档），在很暗的区间可能看出轻微台阶。

**本周最终建议值：`TICK_MS = 1`、`TICKS = 20`。** 如果觉得台阶粗，可以折中试 `TICKS = 25`（40Hz、4% 一档）或 `TICKS = 50`（20Hz，仍能看出一点闪）。

记录你的取舍：为什么不能既要 100 档又要 50Hz？（因为 tick 最小 1ms，频率和份数成反比。）

### 6.5 回调纪律：10 行、三类东西不许出现

回调里**不要**出现：

| 禁止项 | 原因 |
|---|---|
| `time.sleep` / `sleep_ms` / `sleep_us` | 中断里等待会把整个系统拖住，下一次中断和主循环都会迟到 |
| `print` | 串口输出很慢，还会分配内存，最容易把节拍拖垮 |
| 大循环、大计算、频繁创建列表/对象 | 回调一长，主循环和下一次中断都被推迟，波形抖动 |

正确分工：**回调只更新计数器和引脚电平；所有计算、节奏、打印都放主循环。** 这是嵌入式开发的第一条纪律。

## 7. 第 5 关：一个定时器带三路

**目标**：把单路的计数器和引脚扩展成三路，仍然只用**一个**定时器；写通用循环，不许把赋值抄三遍。

### 7.1 用列表管三路

```python
LED_PINS = (10, 11, 12)                 # R、G、B
leds = [Pin(p, Pin.OUT) for p in LED_PINS]
counters = [0, 0, 0]
duty_r = duty_g = duty_b = 0
```

- `leds[0]`、`leds[1]`、`leds[2]` 分别对应红、绿、蓝；
- `counters` 三个元素各自独立计数；
- `duty_r` / `duty_g` / `duty_b` 是任务书要求的三个占空比变量，由主循环推进。

### 7.2 通用回调骨架

```python
def on_tick(timer):
    duties = (duty_r, duty_g, duty_b)
    for k in range(3):
        counters[k] = (counters[k] + 1) % ____
        on = duties[k] * ____ // 100
        leds[k].value(1 if counters[k] < on else 0)
```

要点：

- `duties = (duty_r, duty_g, duty_b)` 在每次回调开始时取一个**快照**，循环里只用快照，逻辑简单；
- `counters[k]` 是可变列表元素，回调里改它不需要 `global`（没有重新绑定 `counters` 这个名字）；
- 整个回调 6 行（含 `def`），满足“不超过 10 行”；
- 三路共用一个定时器，没有开三个 `Timer`。

### 7.3 先测固定颜色

主循环临时写：

```python
duty_r, duty_g, duty_b = 100, 0, 0      # 红
while True:
    pass
```

逐个确认：

| `duty_r, duty_g, duty_b` | 预期颜色 |
|---|---|
| 100, 0, 0 | 红 |
| 0, 100, 0 | 绿 |
| 0, 0, 100 | 蓝 |
| 100, 100, 0 | 黄 |
| 0, 100, 100 | 青 |
| 100, 100, 100 | 白 |

如果某一路不亮，回到第 0 关查那一颗电阻、那根线、那个 GPIO 号。

### 7.4 共享变量的注意点（任务书提示 7）

- `counters`、`leds` 只在回调里被写，主循环不碰，安全；
- `duty_r/g/b` 由主循环写、回调读。MicroPython 里**单个 int 的赋值/读取是原子操作**，本任务够用；
- 回调把三个 int 取成一个元组时，理论上可能碰上主循环刚改完一个、还没改下一个的瞬间，但最多影响一个 1ms 的 tick，肉眼不可见；
- 以后如果共享的是列表/字典/自定义对象，就要更小心（比如主循环先改一半被中断）。本周记住“**能简单就别复杂**”。

## 8. 第 6 关：三种效果

**目标**：主循环按时间推进 `duty_r/g/b`，循环播放任务书要求的三种效果。

先加一个统一入口，避免三路赋值写散：

```python
def set_duty(r, g, b):
    global duty_r, duty_g, duty_b
    duty_r, duty_g, duty_b = r, g, b
```

### 8.1 效果一：红、绿、蓝各自单独呼吸一轮

用三个 `for` 循环，一次只让一路亮，从 0 升到 100 再降回 0：

```python
def breathe_one(k):
    color = [0, 0, 0]
    for d in range(0, 101, DUTY_STEP):
        color[k] = ____
        set_duty(color[0], color[1], color[2])
        time.sleep_ms(BREATH_MS)
    for d in range(100, -1, -DUTY_STEP):
        color[k] = ____
        set_duty(color[0], color[1], color[2])
        time.sleep_ms(BREATH_MS)
```

调用方式：

```python
for k in range(3):
    breathe_one(k)
```

效果：红呼吸一轮 → 绿呼吸一轮 → 蓝呼吸一轮。每一轮结束时该路回到 0，下一轮从 0 开始，衔接自然。

### 8.2 效果二：三路错相位呼吸，颜色流转

思路：三路都用同一个三角形波，但相位彼此错开 1/3 个周期。任何时刻三路亮度不同，混出来的颜色就会随时间连续变化，形成“色环流转”。

三角波（整数写法，`x` 取 0–99）：

```text
x = 0    → 0
x = 50   → 100
x = 99   → 98
公式：tri(x) = 100 - abs(2 * x - 100)
```

三路相位错开约 120°（`0`、`33`、`66`）：

```python
def color_wheel():
    for phase in range(0, 100, PHASE_STEP):
        color = [0, 0, 0]
        for k in range(3):
            x = (phase + k * ____) % 100
            color[k] = 100 - abs(2 * x - ____)
        set_duty(color[0], color[1], color[2])
        time.sleep_ms(BREATH_MS)
```

- `PHASE_STEP` 控制颜色流转快慢，先取 1；
- 一个完整色环 = 100 个 phase × `BREATH_MS`，取 20ms 时约 2 秒转一圈；
- 颜色会连续过渡，大致经过红、黄、绿、青、蓝、紫（具体顺序和起始相位有关）；
- 因为三角波在顶点附近另外两路也有约 30% 亮度，颜色会比纯色“淡”一些，这是这种写法的正常现象。

> 想更接近“纯红纯黄”的色环，可以改用 6 个关键色查表再做整数插值，作为学有余力的扩展；本周先用三角波把“错相位”讲清楚。

### 8.3 效果三：固定橙色整体呼吸

固定比例 `ORANGE = (100, 30, 0)`，三路同时按同一个呼吸系数缩放：

```python
ORANGE = (100, 30, 0)


def breathe_color(color):
    for d in range(0, 101, DUTY_STEP):
        set_duty(color[0] * d // 100, color[1] * d // 100, color[2] * d // 100)
        time.sleep_ms(BREATH_MS)
    for d in range(100, -1, -DUTY_STEP):
        set_duty(color[0] * d // 100, color[1] * d // 100, color[2] * d // 100)
        time.sleep_ms(BREATH_MS)
```

- `d` 是整体亮度 0–100，三路按自己的比例同步缩放；
- 所以橙色始终是“红 100、绿 30、蓝 0”的比例，只是整体变亮变暗。

### 8.4 主循环把三种效果串起来

```python
while True:
    for k in range(3):
        breathe_one(k)
    color_wheel()
    breathe_color(ORANGE)
```

一个循环大约 12s（效果一）+ 2s（效果二）+ 4s（效果三）≈ 18 秒，然后从头再来。

### 8.5 关于“无跳变”

- 效果一和效果三都是从黑开始、回到黑，前后衔接自然；
- 效果二本身不是从黑开始（三角波三路不会同时为 0），从效果一切到效果二、从效果二切到效果三时，理论上会有一次颜色跳变；
- 如果老师严格要求“整个循环无跳变”，可以在进入/退出效果二时把三路整体亮度乘一个 0→100→0 的渐变系数（选做），但会增加代码量。先保证每个效果内部过渡连续。

## 9. 第 7 关：CPU 没闲着——串口打印

**目标**：证明“中断管波形、主循环管杂活”可以并行不悖。

### 9.1 为什么不能直接在回调里 `print`

`print` 要经过串口，速度比 1ms 慢得多，还会分配内存。如果放在回调里：

- 回调执行时间暴涨，下一次 1ms 中断被推迟；
- 主循环也被长期打断；
- 波形抖动、呼吸卡顿，严重时看起来像死机。

所以所有打印都放主循环。

### 9.2 用一个 `beat()` 统一节拍

主循环里每个效果都有 `time.sleep_ms(BREATH_MS)`。把它换成一个统一函数，在每次“拍子”后顺便检查要不要打印：

```python
last_print = time.ticks_ms()


def beat():
    global last_print
    time.sleep_ms(BREATH_MS)
    now = time.ticks_ms()
    if time.ticks_diff(now, last_print) >= PRINT_MS:
        print("duty r/g/b =", duty_r, duty_g, duty_b)
        last_print = now
```

- `PRINT_MS = 2000`，写在文件开头；
- 用 `time.ticks_ms()` + `time.ticks_diff()`，避免计数器回绕问题；
- 把第 6 关所有 `time.sleep_ms(BREATH_MS)` 都替换成 `beat()`；
- 回调一行都不用改——这正是职责分离的好处。

### 9.3 观察

在 Wokwi 里打开串口监视器，应该看到类似：

```text
duty r/g/b = 0 0 0
duty r/g/b = 37 0 0
duty r/g/b = 82 0 0
duty r/g/b = 100 30 0
...
```

数字每 2 秒左右刷一次，同时灯继续正常呼吸、流转，**没有卡顿**。因为波形是定时器产生的，主循环打印慢一点也只影响“数字刷新”，不影响波形。

### 9.4 回答老师的两个问题

**问题一：把回调里的“计数比较”改成“每次中断直接翻转引脚”，输出会变成什么波形？**

每 1ms 翻转一次：高 1ms、低 1ms → 周期 2ms → **500Hz 方波，占空比固定 50%**。此时改 `duty` 没有任何效果，因为没有比较逻辑了，只能输出固定频率、固定占空比的方波。`TICK_MS` 改成 2 就变成 250Hz，以此类推。

**问题二：为什么回调里不能用 `time.sleep`、不能做大计算？**

回调运行在中断上下文，它“插队”执行时主循环是停住的。回调里等待或做大计算，会让：

- 当前中断迟迟不返回，主循环被冻结；
- 下一次定时器中断被推迟甚至丢失，波形周期和占空比都失真；
- 整个系统的实时性被破坏。

所以回调只做“计数 + 比较 + 写引脚”这种微秒级的小事，其余都放主循环。

### 10.4 可选：`Timer.ONE_SHOT` 极简版

想体会周期模式和单次模式的区别，可以把回调改成每次重新武装自己：

```python
def on_tick(timer):
    global count
    count = (count + 1) % TICKS
    led.value(1 if count < duty * TICKS // 100 else 0)
    timer.init(period=TICK_MS, mode=Timer.ONE_SHOT, callback=on_tick)
```

- `ONE_SHOT` 只触发一次，所以每次回调结束前要重新 `init` 才能继续；
- 效果上类似周期模式，但每次都要重新排队，开销更大、抖动更明显；
- 结论：能用 `PERIODIC` 就别用 `ONE_SHOT` 手工续命。

## 12. 常见故障排查

| 现象 | 先查什么 | 常见原因 |
|---|---|---|
| 灯完全不亮 | 共阴、COM、GP10、220Ω | 还是默认共阳；COM 接 3V3；引脚号写错；仿真没运行 |
| 灯不闪，常亮/常灭 | 定时器模式 | 忘了 `mode=Timer.PERIODIC`，默认 `ONE_SHOT` 只触发一次 |
| 运行报 `TypeError` | 回调签名 | `def on_tick():` 少了 `timer` 参数 |
| 报 `NameError: local variable referenced before assignment` | 回调里的全局变量 | 第 3 关漏写 `global count`（CPython 下显示为 `UnboundLocalError`，含义相同） |
| 只有全亮/全灭两档 | duty 是否在变 | 主循环没写循环；`duty` 写死；`on` 恒为 0 或 `TICKS` |
| 明显闪烁 | `TICK_MS × TICKS` | 频率太低；把 `TICKS` 调小（如 20） |
| 亮度台阶很粗 | `TICKS` 太小 | 频率和分辨率取舍；可折中 25 或 50 |
| 呼吸底部有跳变 | 反向 range | 写了 `range(100, 0, -1)`，漏掉 0；终点应为 -1 |
| 呼吸快到看不清 | 主循环 sleep | `BREATH_MS` 太小，或按验收实验把 sleep 改成了 `pass` |
| 呼吸/流转偶尔“卡一下” | 主循环里的长操作 | 某段代码执行太久拖慢了 duty 更新；print、大计算、长循环都放主循环也要注意别太久 |
| 加打印后灯卡顿 | print 位置 | print 放进了回调；应放主循环（`beat()`） |
| 三路只亮一路 | 引脚列表、接线 | `LED_PINS` 写错；绿/蓝电阻或线没接；共阳 |
| 颜色跳变 | 相位公式 | `% 100` 或偏移写错；效果二起止不是黑色 |
| 串口没输出 | 串口监视器、`PRINT_MS` | 没打开串口监视器；打印条件没触发 |
| 在线工程丢失 | 账号、保存 | 未登录；未点保存 |

### 排错总顺序

```text
单路接线 → 定时器是否在跑 → 回调计数/比较 → duty 是否在变 → 频率/份数 → 三路接线 → 效果调度 → 打印位置
```

每修好一个问题，可以在自己的笔记里记一行“现象 → 原因 → 改法”。

- [ ] 沿用上周工程，红灯串 220Ω 接 GP10，RGB 灯为共阴；
- [ ] `TICK_MS`、`TICKS`、`DUTY_STEP`、`BREATH_MS` 是文件开头的命名常量；
- [ ] 回调维护计数器，计数 < 占空比输出高，计满清零；
- [ ] duty 从 0 → 100 → 0，红灯平滑呼吸，无明显闪烁；
- [ ] 改 `TICK_MS` 后波形周期变化，能口头说明 PWM 频率怎么算；
- [ ] 固定 duty、主循环 `pass` 时波形仍在，能解释“波形归定时器、节奏归主循环”；
- [ ] 回调不超过 10 行，没有 `sleep`、`print`；
- [ ] 最大缩进不超过三层。

### 任务二

- [ ] 一个定时器回调同时更新 GP10/GP11/GP12，三路各有计数器；
- [ ] `duty_r` / `duty_g` / `duty_b` 由主循环推进；
- [ ] 三种效果循环播放：三色单独呼吸、错相位彩色流转、固定橙色整体呼吸；
- [ ] 颜色过渡连续，没有明显跳变；
- [ ] 主循环每 2 秒打印三个 duty，打印期间灯不卡顿；
- [ ] 三路电平更新用循环/列表遍历，没有抄三遍赋值；
- [ ] 能回答“每次中断翻转引脚会得到什么波形”；
- [ ] 能解释回调里为什么不能 `sleep`、不能做大计算。

### 交付

- [ ] 在线仿真中完整循环播放；
- [ ] 代码已同步回仓库 `work 03/main.py`。

## 15. 给队友的建议

- 每个人可以新建自己的分支，例如 `work3/你的名字`，在各自分支里完成 `main.py`，不要互相覆盖；
- 仓库里的 `main.py` 是已验证的最终实现；学习时按各关自己写，写完再对照，不要一开始就抄；
- 先自己写，再看指南里的填空；卡住 20 分钟以上再升级提示；
- 每完成一关就提交一次，提交信息写清楚“第几关 + 做了什么”；
- 遇到问题先查第 12 节，再在群里贴“现象 + 代码 + 报错”；
- 本周最重要的不是“灯好看”，而是能讲清楚：**中断里做什么、主循环做什么、为什么必须这样分**。
