## 3. 第 1 关：闪烁基线

### 知识点

- `Pin(10, Pin.OUT)`：把 **GP10** 设成输出。`10` 是 GPIO 编号，不是物理第 10 脚。
- `.value(1)`：输出高电平；共阴灯对应颜色点亮。
- `.value(0)`：输出低电平，熄灭。
- `time.sleep_ms(500)`：等待 500 毫秒。

```python
while True:
    led.value(____)        # 点亮
    time.sleep_ms(____)    # 亮 0.5 秒
    led.value(____)        # 熄灭
    time.sleep_ms(____)    # 灭 0.5 秒
```

参考运行结果：红灯亮 0.5 秒、灭 0.5 秒，循环。

## 4. 第 2 关：理解 PWM

**目标**：在写代码前，能用自己的话说清“周期、频率、占空比、平均功率”。

### 4.1 为什么不能直接“调低电压”

Pico 的 GPIO 只有高（约 3.3V）和低（0V）两种状态，不能输出 1.65V 这样的中间电压。要让灯“半亮”，只能快速地在亮和灭之间切换：

- 亮的时间占比高 → 平均功率大 → 看起来亮；
- 亮的时间占比低 → 平均功率小 → 看起来暗。

这就是**脉冲宽度调制（PWM）**：周期固定，改变高电平在一个周期里所占的比例。

### 4.2 四个关键词

| 名称 | 符号 | 含义 | 本周取值 |
|---|---|---|---|
| 周期 | T | 一个完整方波的时间 | 20ms |
| 频率 | f = 1/T | 每秒多少个周期 | 1 / 0.02s = 50Hz |
| 份数 | N | 一个周期切成多少份 | 100 |
| 每份时长 | T/N | 每一份持续多久 | 20ms / 100 = 0.2ms |
| 占空比 | duty | 一个周期里高电平占的比例 | 0% → 100% → 0% |

### 4.3 算一遍

- T = 20ms = 0.02s；
- f = 1 / 0.02 = 50Hz；
- N = 100 份，每份 = 20ms / 100 = 0.2ms = 200µs；
- duty = 50%：前 50 份输出高、后 50 份输出低，高电平共 10ms，平均电压约 1.65V；
- duty = 0：100 份全低，灯灭；
- duty = 100：100 份全高，灯最亮。

### 4.4 为什么眼睛看到的是“亮度”而不是“闪烁”

50Hz 意味着每秒切换 50 个周期。人眼对这么快的变化有视觉暂留，看到的是平均效果，而不是一次次亮灭。N = 100 意味着亮度有 101 个档位（0 到 100），档位越多，呼吸越平滑。

### 验收

- [ ] 能算出每份 0.2ms；

## 5. 第 3 关：写“一帧”PWM

**目标**：写一个函数，输入 duty，输出一个完整周期的 PWM 波形。

### 5.1 先写内层循环

一个周期要做 N 次判断：第 i 份亮不亮，取决于 `i` 是否小于“应该亮的份数”。

```text
重复 N 次：
    如果 i < 亮的份数 → 输出 1
    否则             → 输出 0
    等待一份的时长
```

任务要求把这个判断写成**一行条件表达式**，不要写成 if/else 两段：

```python
led.value(1 if i < on else 0)
```

这行的意思是：条件成立取 `1`，否则取 `0`。

### 5.2 命名常量与每份时长

在文件开头定义：

```python
T_MS = ____          # 周期，毫秒
N = ____             # 一个周期的份数
STEP_US = T_MS * 1000 // N   # 每份多少微秒
```

`STEP_US` 就是任务书要求的“每份时长”常量。默认值下它等于 `20 * 1000 // 100 = 200`，即 200µs。

### 5.3 0.2ms 的坑：sleep_ms 只收整数毫秒

任务书伪代码写的是 `time.sleep_ms(每份毫秒数)`，但每份是 **0.2ms**，而 MicroPython 的 `time.sleep_ms()` 只处理整数毫秒：

```python
time.sleep_ms(0.2)   # 错误：得不到 0.2ms，会报错或被当成 0
time.sleep_us(200)   # 正确：200 微秒 = 0.2ms
```

如果每份实际等待 0，内层循环会瞬间跑完，周期远小于 20ms，亮度、闪烁都会不对。**本周统一用 `time.sleep_us(STEP_US)`。**

> 补充：Python 循环本身也有少量开销，仿真里实际周期会略大于 20ms，属正常现象。不要为了“凑准”把 `sleep_us` 改成 0。

### 5.4 duty 百分比怎么变成“亮的份数”

任务书里 duty 是 0 到 100 的百分比，而内层循环数的是 0 到 N-1 份。用一行换算：

```python
on = duty * N // 100
```

- N = 100 时，`on` 正好等于 `duty`，和任务书伪代码完全一致；
- N 改成 20 时，duty 仍然是 0 到 100，`on` 会折算成 0 到 20，不会出现“duty 大于 N 后一直全亮”的饱和问题；
- `//` 是整数除法，保证 `on` 是整数。

### 5.5 填空骨架

```python
from machine import Pin
import time

T_MS = ____                  # 20
N = ____                     # 100
STEP_US = T_MS * 1000 // N   # 每份微秒数

led = Pin(10, Pin.OUT)

def frame(duty):
    on = ____ * N // 100
    for i in range(____):
        led.value(____ if i < ____ else ____)
        time.sleep_us(____)
```

### 5.6 单独测试这一帧

先不要写呼吸，把 duty 固定住，确认一帧是对的：

```python
while True:
    frame(50)
```

现象：红灯以半亮稳定发光，不闪。再试 `frame(0)`（灭）、`frame(100)`（最亮）、`frame(10)`（很暗）。

### 验收

- [ ] `frame(0)` 全灭，`frame(100)` 最亮，`frame(50)` 约为半亮；
- [ ] 亮灯判断是一行 `1 if ... else 0`，没有 if/else 两段；
- [ ] 用 `sleep_us`，不是 `sleep_ms(0.2)`；
- [ ] 能说出 `on = duty * N // 100` 每一部分的作用；
- [ ] 固定 duty 时灯稳定，没有明显闪烁。

### 排错顺序

**红灯接线 → frame(0)/frame(100) 是否分别全灭/全亮 → duty 换算 → sleep_us 数值 → 周期是否约 20ms**。

## 6. 第 4 关：让 duty 呼吸

**目标**：在外层扫描 duty，把固定亮度变成“暗 → 亮 → 暗”。

### 6.1 两个方向

呼吸 = 先让 duty 从 0 加到 100，再从 100 减回 0。用两个 `for` 循环：

```python
DUTY_STEP = ____   # 每次变化几个百分点，先填 1

while True:
    for duty in range(0, 101, DUTY_STEP):
        frame(____)
    for duty in range(100, -1, -DUTY_STEP):
        frame(____)
```

要点：

- `range(0, 101, 1)` 产生 0, 1, 2, …, 100，**右端 101 不包含**，所以能取到 100；
- 反向要写 `range(100, -1, -1)`，终点写 **-1** 才能取到 0；
- 写成 `range(100, 0, -1)` 会漏掉 0，下一轮又从 100 突然开始，底部会有一次跳变。

### 6.2 呼吸一次要多久

- 上升：101 帧 × 20ms ≈ 2.02s；
- 下降：101 帧 × 20ms ≈ 2.02s；
- 一个完整呼吸约 **4 秒**。

如果觉得太慢，改 `DUTY_STEP = 2` 或 `5`（选能整除 100 的数），不要靠改 `T_MS` 来调速度——`T_MS` 决定的是 PWM 频率。

### 6.3 缩进检查

任务要求最大缩进三层，即行首最多 12 个空格。当前结构是两层：

```python
while True:                     # 0 个空格
    for duty in range(...):     # 4 个空格
        frame(duty)             # 8 个空格
```

函数内部也是两层：

```python
def frame(duty):                # 0 个空格
    for i in range(N):          # 4 个空格
        led.value(...)          # 8 个空格
```

再套一层 `if` 会到 12 个空格，仍在“三层”以内；但本周的亮灯判断已经用条件表达式，不需要这个 `if`。到 16 个空格就是四层，超限。

### 验收

- [ ] 红灯从暗逐渐变亮，再逐渐变暗，循环播放；
- [ ] 亮度变化连续，没有突然跳变；
- [ ] `range(100, -1, -DUTY_STEP)` 能回到 0；
- [ ] 最大缩进不超过三层；
- [ ] 亮灯判断仍是一行条件表达式。

## 7. 第 5 关：调参实验、同步、总结

### 7.1 实验一：只改 N（任务书验收第 2 条）

把 `N` 从 100 改成 20，其他常量不动，重新运行：

| 项目 | N = 100 | N = 20 |
|---|---|---|
| 每份时长 `STEP_US` | 200µs | 1000µs |
| 一个周期的份数 | 100 | 20 |
| 可用亮度档位 | 101 档 | 21 档 |
| 呼吸一次的时长 | 约 4s | 约 4s |
| 现象 | 平滑 | 能看出台阶 |

记录你的解释：

- 为什么速度没怎么变？因为外层仍然是 101 个 duty 值，每帧仍然是 20ms；
- 为什么平滑度变差？因为一个周期只有 20 份，duty 要变化约 5 个百分点，`on` 才增加 1，亮度只能按 5% 的台阶跳，而且每一级会停留约 5 帧（100ms）；
- 所以 **N 决定亮度分辨率**，N 越大越细腻，但内层循环也越长。

> 注意：如果你没有写 `on = duty * N // 100`，而是直接用 `i < duty`，改成 N = 20 后 duty 一旦超过 20 就一直全亮，现象会完全不同。这也是第 5.4 节要折算的原因。

### 7.2 实验二：改 T

把 `T_MS` 从 20 改成 10，观察：

- `STEP_US` 自动变成 100µs；
- PWM 频率变成 100Hz；
- 每帧时间减半，呼吸一次约 2 秒；
- 频率更高，理论上更不容易看到闪烁。

再试 `T_MS = 50`（20Hz）：呼吸更慢，但如果能看出闪烁，说明频率太低。记录现象和解释。

### 7.3 实验三：改 DUTY_STEP

把 `DUTY_STEP` 从 1 改成 2 或 5：

- 每次 duty 跳得更大，呼吸更快；
- 台阶可能变粗；
- `range` 的步长必须和 100 配合，最好选能整除 100 的数。

1. 把 Wokwi 在线版验证通过的 `main.py` 复制到 `work 02/main.py`；
2. 如果改过接线，把 `diagram.json` 也同步回来；

## 9. 常见故障排查

| 现象 | 先查什么 | 常见原因 |
|---|---|---|
| 红灯完全不亮 | `common` 属性、COM 接线、GP10 | 还是默认共阳；COM 接 3V3；引脚号写成别的；仿真没运行 |
| 只有全亮/全灭两档 | duty 是否真的在变 | 外层没写循环；`frame` 里 duty 写死；`on` 被固定成 0 或 100 |
| 灯常亮不呼吸 | `on` 的计算和 range | `i < on` 写反；duty 一直是 100；`range` 端点写错 |
| 明显闪烁、抖动 | T、N、每份时长 | T 太大（频率低）；N 太小；每份 sleep 太长 |
| 内层循环瞬间跑完 | `sleep` 的参数 | 用了 `sleep_ms(0.2)`，被当成 0；应改用 `sleep_us(STEP_US)` |
| 改 N 后亮度异常、一直全亮 | `on` 的换算 | 直接写 `i < duty`，duty 大于 N 后饱和；应写 `on = duty * N // 100` |
| 呼吸底部有跳变 | 反向 range | 写了 `range(100, 0, -1)`，漏掉 0；终点应为 -1 |
| 呼吸太快/太慢 | `DUTY_STEP` | 步进太大或太小；不要用 T 调呼吸速度 |
| 报 TypeError 或参数错误 | sleep 函数 | `sleep_ms` 收到小数；改用 `sleep_us` 整数微秒 |
| 在线工程丢失 | 账号、保存 | 未登录；未点保存 |

### 排错总顺序

```text
红灯接线 → frame(0)/frame(100) → 固定 duty 是否稳定 → duty 是否在扫描 → 常量与 range 端点
```

每修好一个问题，可以在自己的笔记里记一行“现象 → 原因 → 改法”。
